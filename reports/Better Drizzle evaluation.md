# Skip Better Drizzle and keep Kysely

Better Drizzle (`better-drizzle` on npm) is a free, Apache-2.0, single-maintainer library. It wraps a live Drizzle ORM client in a Prisma-style repository API (`client.users.findMany({ where, include })`, `paginate`, `cursor`, nested relation writes, plugins). It is not a schema, migration, codegen or Studio tool, so it does nothing for the half of Drizzle that BenPlate uses. Its value comes only from running queries through Drizzle, and BenPlate deliberately runs every query through Kysely. **BenPlate should not adopt it.** Keeping Kysely means it adds a second query layer that would duplicate Kysely. Replacing Kysely means trading away the query DX the developer prefers, in exchange for a 3.5-month-old API with a bus factor of one. It would also tie BenPlate's Drizzle upgrades to one person's release schedule: 0.3.0 accepts only `drizzle-orm` rc.4, and as of 2026-10-07 0.3.0 cannot be installed from npm because the maintainer is locked out of his npm account. Cost is not the issue, since the library is free. The real costs are a second runtime and a hard pin on a specific Drizzle RC. The project is too young to have a meaningful track record, but its release history already includes a wrong-results bug that stayed in the npm `latest` version for two months. For the pending `updated_at` decision, Better Drizzle's own timestamps plugin argues for keeping database triggers: app-side timestamps only cover writes that pass through that one layer.

## Better Drizzle is a Prisma-style query layer, not a schema tool

The project calls itself "Drizzle ORM, without the glue" and promises "relation filters, nested includes, pagination, relation writes and plugins for every table", "zero codegen", on PostgreSQL, MySQL and SQLite ([better-drizzle.com](https://better-drizzle.com/)). Its own docs describe the architecture: it "generates a repository API from the Drizzle schema you already have… Queries compile to Drizzle and run on your driver, and raw Drizzle stays one line away" ([Why better-drizzle?](https://better-drizzle.com/docs/why)). Setup is `better(drizzle({ client, relations }))`. **A Drizzle instance without a `defineRelations` config throws** ([changelog](https://better-drizzle.com/docs/changelog)). The source builds every read and write with that Drizzle instance's `select`/`insert`/`update` builders and contains no Kysely integration ([GitHub src](https://github.com/almeidazs/better-drizzle/tree/main/src)).

On top of reads (`findMany`, `findUnique`, `count`, `exists`, `paginate`, `cursor`) it adds a large write surface: `upsert` via native `ON CONFLICT`, `createMany`/`upsertMany` in batches, `updateEach` as a single `CASE` statement, nested `connect`/`disconnect`/`set`, and atomic `increment`/`toggle`. It also offers transactions with savepoints and automatic deadlock retries, row locks, and `.explain()`, which returns the SQL and the query plan ([support matrix](https://better-drizzle.com/docs/reference/support-matrix); [README](https://github.com/almeidazs/better-drizzle/blob/main/README.md)). Plugins cover soft delete, timestamps, Zod schemas, runtime "rules" guardrails with an ESLint counterpart, and an experimental Redis cache ([README](https://github.com/almeidazs/better-drizzle/blob/main/README.md)). The documented gaps matter for a SQL-minded developer: **no `groupBy` or aggregates beyond count, `orderBy` on plain columns only, and plugin transforms such as soft-delete filters or tenant scoping apply only to the root query, not to `include`d relations** ([Limitations](https://better-drizzle.com/docs/guides/limitations)).

Cost is zero. The library is Apache-2.0, with no paid tier, hosted component or account, and a keyword grep of the source found no telemetry ([LICENSE](https://github.com/almeidazs/better-drizzle/blob/main/LICENSE); [repo src/](https://github.com/almeidazs/better-drizzle/tree/main/src)). Supply-chain hygiene is good: zero runtime dependencies, no install scripts, and SLSA provenance on published versions ([npm 0.2.0 manifest](https://registry.npmjs.org/better-drizzle/0.2.0); [attestations](https://registry.npmjs.org/-/npm/v1/attestations/better-drizzle@0.2.0)). The author is Hiago Almeida (`almeidazs`), an independent developer in Brazil. Funding is a Neon sponsorship of unknown size plus one GitHub Sponsor, and **nothing links the project to drizzle-team or to Better Auth**, despite the name ([GitHub profile](https://github.com/almeidazs); [GitHub Sponsors](https://github.com/sponsors/almeidazs)).

## It fixes Drizzle's query glue, not the schema-side pain BenPlate deals with

What BenPlate maintains by hand sits on the schema side: per-table `updated_at` triggers in custom SQL migrations, drizzle-kit rename prompts, push/migrate drift, and keeping kysely-codegen in sync. Better Drizzle touches none of it. A search of its source and all 54 docs pages finds no migration code. drizzle-kit appears only as the user's own tool, for example "generate the migration with drizzle-kit as usual" ([arrays docs](https://better-drizzle.com/docs/querying/arrays)). The project says outright that "your schema remains the source of truth" ([Limitations](https://better-drizzle.com/docs/guides/limitations)). A CLI exists only as a one-word feature request ([Issue #52](https://github.com/almeidazs/better-drizzle/issues/52)).

| Drizzle pain point                                                                                                                       | Better Drizzle's answer                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `$onUpdate` / `$defaultFn` are runtime-only and invisible to drizzle-kit ([Drizzle docs](https://orm.drizzle.team/docs/column-types/pg)) | A `timestamps` plugin that is also runtime-only, covering only its own delegates. Not a fix                                    |
| Triggers and functions in migrations, custom SQL migrations                                                                              | None. drizzle-kit `--custom` stays the tool ([Drizzle custom migrations](https://orm.drizzle.team/docs/kit-custom-migrations)) |
| Rename prompts, push vs migrate drift, safe index creation, RLS, enums, identity columns, Studio, seeding                                | None                                                                                                                           |
| Type generation                                                                                                                          | No codegen; types are inferred from `typeof relations`. Replaces kysely-codegen only if Kysely is dropped                      |
| Verbose relational reads and pagination in raw Drizzle                                                                                   | **Fixed**: `include`, `some`/`every`/`none` filters, per-parent `take`, `_count`, `paginate`, `cursor`                         |
| No relational writes or upsert helpers in Drizzle                                                                                        | **Fixed**: nested writes, `upsertMany`, `updateEach`, atomic updates                                                           |
| Repository boilerplate (soft delete, guardrails)                                                                                         | **Fixed** via plugins, with the root-query-only caveat                                                                         |

Drizzle 1.0 has also absorbed much of the read-side pitch. Relational queries v2 already filter by relations, support many-to-many through `.through()`, and offset/limit related rows ([Drizzle relations v1→v2](https://orm.drizzle.team/docs/relations-v1-v2)). What Better Drizzle uniquely adds today is mostly the write side and the plugin system. One upstream relation feature is missing: **relations with a relation-level `where` throw `cannot be loaded`**, and Drizzle's own `db.query` handles them instead ([v0.3.0 release notes](https://github.com/almeidazs/better-drizzle/releases/tag/v0.3.0)).

## Adopting it means a second query layer, or giving up Kysely

Better Drizzle requires a Drizzle runtime, so BenPlate has two options, and both are poor. **Complementing Kysely** would take about a day: write a `relations.ts` with `defineRelations` for every table, build `drizzle({ client: pool, relations })` on the existing `pg` pool, and wrap it with `better()`. The result is two query APIs, two sources of types (introspected `db.ts` and schema inference), two error shapes (Drizzle 1.x wraps driver errors in `DrizzleQueryError`) and no shared transactions between the two libraries ([Upgrading guide](https://better-drizzle.com/docs/guides/upgrading)). It would also break the project rule that "Kysely runs the queries", and Drizzle's `$onUpdate` hooks would start firing on some writes and not others. **Replacing Kysely** means rewriting every handler in `packages/api`. It also means moving Better Auth from the app's Kysely instance to `@better-auth/drizzle-adapter/relations-v2`, re-verifying the startup auth schema check, and dropping kysely-codegen and CamelCasePlugin ([Better Auth Drizzle adapter](https://www.better-auth.com/docs/adapters/drizzle)). That takes days to weeks. Afterwards every call site speaks a Prisma-shaped dialect that the developer does not prefer, and leaving again would mean another full rewrite of the query layer. Schema lock-in stays at zero on either path, because tables and migrations remain plain Drizzle.

The rest of the stack offers it little. The `zod` plugin is useless here: the oRPC contract uses hand-written Valibot schemas and must never import database code into the browser. The ids need custom work too. Better Drizzle's `create` would leave the private identity id to the database as any Drizzle insert does, but the public prefixed nanoid still needs a custom plugin or `extends()` wrapper. Snake-case casing via `snakeCase.table` should come from Drizzle's builder, but no doc or test confirms it. `.explain()` builds its own config with raw column names, which could render camelCase keys incorrectly (unverified) ([GitHub src](https://github.com/almeidazs/better-drizzle/tree/main/src)). Pinning to rc.4 looks like a match for BenPlate's catalog, but it is a trap. **0.3.0 accepts only `>=1.0.0-rc.4 <1.0.0-rc.5` "because the typecheck fails against that snapshot"**, so adopting it would freeze BenPlate on rc.4 until the maintainer ships again ([v0.3.0 release notes](https://github.com/almeidazs/better-drizzle/releases/tag/v0.3.0)). For a developer who wants bleeding-edge tooling, the problem is not the pre-release label. The problem is a dependency that blocks staying current.

The alternatives in the notes point the same way. They all trade away something the developer explicitly values:

| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |

## Performance claims come from in-memory SQLite and don't transfer to Postgres

All published numbers are the vendor's own, produced with Bun on **in-memory SQLite "to isolate wrapper overhead from I/O"** ([Benchmarks](https://better-drizzle.com/docs/performance/benchmarks)). On that setup, reads cost +2.8% to +11.3% over raw Drizzle, writes +3–4%, and transactions roughly ±9%. Heap use for mixed reads rises **+165% to +210%** ([Benchmarks](https://better-drizzle.com/docs/performance/benchmarks)). The project's own headline figures disagree with each other. The homepage claims "~5%" read overhead and a 9.5× relation-graph win ([better-drizzle.com](https://better-drizzle.com/)). The README says 9.1× (10.24 ms → 1.12 ms) and "within ~9%" ([README](https://github.com/almeidazs/better-drizzle/blob/main/README.md)). The benchmarks page says "within ~12%". An older snapshot in the repo shows +28% on a filtered list ([benchmark/README](https://github.com/almeidazs/better-drizzle/blob/main/benchmark/README.md)).

The 9.5× headline compares Better Drizzle's batched loader, which runs one query per relation node, against Drizzle's single-statement RQB v2 on in-memory SQLite, where extra round trips cost nearly nothing ([scenarios.ts](https://github.com/almeidazs/better-drizzle/blob/main/benchmark/scenarios.ts)). On networked Postgres 18, every relation node is another round trip, so the ratio is likely to shrink or reverse. The vendor runs no Postgres latency benchmark, and CI benchmarks only run on Bun ([benchmarks.yml](https://github.com/almeidazs/better-drizzle/blob/main/.github/workflows/benchmarks.yml)). BenPlate's Kysely queries nest with `jsonArrayFrom`/`jsonObjectFrom` in a single statement, which is already the round-trip-optimal shape. Whatever the exact figure, Better Drizzle's overhead would come on top of Drizzle's own runtime, which BenPlate currently does not load at all. No data exists on bundle size, cold start or tsc cost, and the type-level inference over `typeof relations` is deep enough that the tsc cost is worth checking before any adoption.

## One maintainer and a locked npm account are the real risks

The repository was created on 2026-06-22. It has 347 stars, about 825 weekly downloads, and roughly four public dependents, the largest being RexaDB at 105 stars ([GitHub](https://github.com/almeidazs/better-drizzle); [npm downloads](https://api.npmjs.org/downloads/point/last-week/better-drizzle); [RexaDB](https://github.com/RexaDB/RexaDB)). There are no Hacker News threads, independent reviews or named production users ([HN Algolia](https://hn.algolia.com/api/v1/search?query=better-drizzle)). **The author wrote 221 of the last 240 commits (92%), is the only npm maintainer, and merges his own feature PRs within one to three minutes, without review** ([commits](https://github.com/almeidazs/better-drizzle/commits/main); [PR #57](https://github.com/almeidazs/better-drizzle/pull/57)). He answers issues fast, with a median of about five hours, but releases arrive in bursts. There were 3 commits in August against 153 in September. A July "abandoned" scare was answered with "I started a new job" ([Issue #28](https://github.com/almeidazs/better-drizzle/issues/28)).

The bus factor has already caused a failure. On 2026-10-04 the maintainer wrote that he had "lost access to my npm account due to two-factor authentication… I can't publish the new v0.3.0 version right now" ([Issue #61](https://github.com/almeidazs/better-drizzle/issues/61)). Users are packing the release tarball by hand ([Issue #66](https://github.com/almeidazs/better-drizzle/issues/66)). Meanwhile the live docs describe 0.3.0, while `npm i better-drizzle` installs 0.2.0, which crashes on Drizzle 1.0 RC with "Export normalizeRelation doesn't exist" ([Issue #61](https://github.com/almeidazs/better-drizzle/issues/61)). The more serious incident: in 0.1.1, the `some`/`none`/`every` relation filters emitted an uncorrelated `EXISTS` and **"silently return wrong rows. No error is raised"**. An outside contributor fixed it on 2026-07-18, but no npm release shipped the fix until 2026-09-20 ([Issue #26](https://github.com/almeidazs/better-drizzle/issues/26); [PR #27](https://github.com/almeidazs/better-drizzle/pull/27)).

Because the developer does not want tests, these risks get worse. 0.3.0 silently changed semantics: `update()`/`delete()` now change at most one row instead of every matching row, and reads became lazy thenables that never run unless awaited ([v0.3.0 release notes](https://github.com/almeidazs/better-drizzle/releases/tag/v0.3.0)). Changes like these pass a typecheck and show up only in behaviour, and without tests nothing would catch them. The library also reaches into Drizzle internals: 0.1.x broke on `extractTablesRelationalConfig`, and 0.2.0 on `normalizeRelation` ([Issue #14](https://github.com/almeidazs/better-drizzle/issues/14)). That explains the exact RC pin, and it means every Drizzle RC bump can break it again. Stable-1.0 software would carry the same risk if it relied on the same internals, so the pre-release label is not the core problem. The Apache-2.0 license and zero dependencies make forking or vendoring a realistic fallback, but vendoring 32,000 lines of TypeScript ([repo](https://github.com/almeidazs/better-drizzle)) to keep a layer BenPlate doesn't need makes no sense.

## The updated_at decision should stay with triggers

Better Drizzle's `timestamps` plugin shows clearly what an app-only `updated_at` gives up. In its default `mode: 'app'`, it "fills timestamp columns before the database call", only for writes through its own delegates, and "always writes its own values", which overwrites anything the caller passed. Raw calls bypass it ([Timestamps plugin](https://better-drizzle.com/docs/plugins/timestamps); [Limitations](https://better-drizzle.com/docs/guides/limitations)). Its `mode: 'database'` is explicitly a no-op "when the database owns timestamps (… triggers…)". In other words, the library defers to triggers when they exist. Drizzle's `$onUpdate` has the same scope problem, since it "is only used at runtime in drizzle-orm" ([Drizzle docs](https://orm.drizzle.team/docs/column-types/pg)), and so would any Kysely plugin. In BenPlate, Better Auth writes through its own adapter calls, and Drizzle Studio edits and SQL seeds bypass the app entirely. **Only a database trigger covers every writer.** Better Drizzle gives no reason to move to app-only `updated_at`. If the per-table trigger boilerplate is the real annoyance, the fix belongs on the migration side, not in a query library: one shared trigger function, with each table's custom migration reduced to a one-line `CREATE TRIGGER`, or Atlas's declarative `triggers.sql` if a Pro licence is acceptable.

## Conclusion

The appeal of Better Drizzle and the design of BenPlate pull in opposite directions. BenPlate deliberately keeps Drizzle out of the runtime and uses it as a DDL compiler, while Better Drizzle exists to make the Drizzle runtime pleasant. The project is also not yet stable enough to justify reversing that decision. One maintainer controls both the code and the npm account, the library depends on Drizzle internals, it is pinned to one RC snapshot, and it has already shipped silent semantic changes in a minor release. Supply-chain hygiene is the one area where it scores well. None of this makes it a bad library for a Drizzle-first codebase that wants Prisma ergonomics. It is the wrong tool for a Kysely-first one.

The useful takeaway is narrower. A few of its ideas are worth copying into Kysely helpers without taking on the dependency: `.explain()` returning the SQL and plan, `cursor()` requiring a unique column as the final sort key (the rule BenPlate's `(createdAt, id)` cursor already follows), `rules`-style guards such as refusing `deleteMany` without a `where`, and typed unique/foreign-key violation helpers. Revisit the decision only if BenPlate ever drops Kysely for Drizzle's own query builder. Even then, first confirm that 0.3.x is actually on npm, that its peer range tracks Drizzle RCs within days, and that someone besides the author can publish.
